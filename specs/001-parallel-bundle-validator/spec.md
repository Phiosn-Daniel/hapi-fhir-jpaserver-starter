# Feature Specification: 平行 Bundle 驗證器 (Parallel Bundle Validator)

**Feature Branch**: `001-parallel-bundle-validator`  
**Created**: 2026-02-06  
**Updated**: 2026-02-08  
**Status**: Draft  
**Input**: User description: "我想要開發一個平行驗證器的功能，再做 bundle json 檔案時，可以自動判斷檔案中entry 下的resource 數量，來決定需要同時啟動多執行續驗證，但要注意CPU 的使用率"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 自動平行驗證 Bundle 中的多筆資源 (Priority: P1)

身為一位系統操作人員，當我提交一個包含大量 entry 的 FHIR Bundle 進行驗證時，系統會自動偵測 entry 下的 resource 數量，並根據數量動態決定啟動多少個並行驗證執行緒，以縮短整體驗證時間。如果 Bundle 只包含少量資源（例如 5 筆以下），系統會採用循序驗證以避免不必要的執行緒開銷。

**Why this priority**: 這是整個功能的核心價值——透過平行處理大幅減少大型 Bundle 的驗證等待時間，直接影響使用者的工作效率與系統吞吐量。

**Independent Test**: 可透過提交不同大小的 Bundle（例如 3 筆、20 筆、100 筆 entry）來獨立驗證系統是否正確選擇循序或平行模式，並確認驗證結果正確完整。

**Acceptance Scenarios**:

1. **Given** 一個包含 50 筆 entry 的 FHIR Bundle, **When** 使用者提交此 Bundle 進行驗證, **Then** 系統自動啟用平行驗證模式，使用多個執行緒同時驗證各筆資源，並在完成後回傳完整的驗證結果（包含每筆資源的驗證狀態）。
2. **Given** 一個包含 3 筆 entry 的 FHIR Bundle, **When** 使用者提交此 Bundle 進行驗證, **Then** 系統採用循序驗證模式處理，避免產生不必要的執行緒管理開銷。
3. **Given** 一個包含 100 筆 entry 的 FHIR Bundle，其中部分資源含有驗證錯誤, **When** 使用者提交此 Bundle 進行驗證, **Then** 系統平行驗證所有資源，個別資源的驗證失敗不影響其他資源的驗證，最終回傳每筆資源各自的驗證結果。

---

### User Story 2 - CPU 使用率自動管控 (Priority: P2)

身為一位系統管理員，我希望平行驗證功能在執行時能自動監控並控制 CPU 使用率，確保驗證過程不會耗盡伺服器資源，影響到其他正在處理的請求或服務。

**Why this priority**: 醫療資訊系統需要維持高可用性，若平行驗證導致 CPU 過載，將影響整體服務品質與其他使用者的操作體驗。

**Independent Test**: 可透過提交超大型 Bundle（例如 500 筆以上 entry）同時監控系統 CPU 使用率，確認系統會自動調節並行數量或排隊處理，CPU 不會長時間超過設定上限。

**Acceptance Scenarios**:

1. **Given** 系統正在平行驗證一個大型 Bundle, **When** CPU 使用率接近設定上限, **Then** 系統自動降低並行執行緒數量或暫停新增執行緒，直到 CPU 使用率回到安全範圍。
2. **Given** 多位使用者同時提交大型 Bundle 進行驗證, **When** 系統 CPU 資源有限, **Then** 系統合理分配並行驗證資源，不會因為單一請求而導致其他請求逾時或失敗。
3. **Given** 系統管理員設定 CPU 使用率上限為 70%, **When** 平行驗證執行中, **Then** 系統 CPU 使用率不會持續超過 70%。

---

### User Story 3 - 平行驗證行為可配置 (Priority: P3)

身為一位系統管理員，我希望能夠透過配置調整平行驗證的行為參數，包括觸發平行驗證的最低資源數量門檻、最大並行執行緒數量、以及 CPU 使用率上限，以便根據不同部署環境的硬體條件進行最佳化。

**Why this priority**: 不同部署環境的硬體資源差異大，提供配置彈性能讓管理員根據實際狀況調整，確保功能在各種環境下都能最佳運作。

**Independent Test**: 可透過修改配置參數後重啟或熱載入，提交相同的 Bundle 驗證請求，確認系統行為確實根據配置改變（例如調低門檻後小型 Bundle 也會啟用平行驗證）。

**Acceptance Scenarios**:

1. **Given** 管理員在配置中將平行驗證門檻設為 10, **When** 提交一個包含 12 筆 entry 的 Bundle, **Then** 系統啟用平行驗證模式。
2. **Given** 管理員在配置中將最大並行執行緒數設為 4, **When** 提交一個包含 200 筆 entry 的 Bundle, **Then** 系統最多同時使用 4 個執行緒進行驗證。
3. **Given** 管理員未修改任何配置（使用預設值）, **When** 提交 Bundle 進行驗證, **Then** 系統使用合理的預設值正常運作。

### User Story 4 - 預建測試資料集自動驗證平行驗證器 (Priority: P4)

身為一位開發人員，當我對平行驗證器的程式碼進行任何修改後，我希望能夠執行一組預先準備好的測試資料集，這些資料集涵蓋各種大小和複雜度的 FHIR Bundle，系統會自動對每個資料集執行驗證，並將結果與預期的基準結果進行比對，以確保我的修改沒有破壞任何現有功能。

**Why this priority**: 在核心功能（P1-P3）完成後，需要一套可靠的回歸測試機制來保護已實作的功能。測試資料集是持續維護品質的第一道防線。

**Independent Test**: 可透過執行測試指令，系統自動載入所有測試資料集、執行驗證、比對結果，並輸出通過/失敗的摘要報告。開發人員只需檢查報告即可確認功能完整性。

**Acceptance Scenarios**:

1. **Given** 專案中已存在一組涵蓋多種情境的測試 Bundle 資料集, **When** 開發人員執行自動化測試指令, **Then** 系統自動載入所有測試資料集，依序或平行執行驗證，並輸出每個資料集的測試結果（通過/失敗）及詳細差異。
2. **Given** 測試資料集包含一個含有 3 筆 entry 的小型 Bundle 和一個含有 100 筆 entry 的大型 Bundle, **When** 自動化測試執行時, **Then** 小型 Bundle 以循序模式驗證、大型 Bundle 以平行模式驗證，且兩者的結果均與預期基準一致。
3. **Given** 開發人員修改了平行驗證器中的執行緒分配邏輯, **When** 執行自動化測試, **Then** 所有測試資料集的驗證結果仍然與基準結果完全一致，確認修改未影響功能正確性。

---

### User Story 5 - 自動偵測失敗並啟動修復流程 (Priority: P5)

身為一位開發人員，當自動化測試偵測到測試失敗時，我希望系統能自動分析失敗原因，嘗試修復問題程式碼，然後自動重新執行測試，重複此流程直到所有測試通過或達到最大嘗試次數，減少我手動除錯的時間。

**Why this priority**: 自動修復能力是提升開發效率的加速器。在擁有可靠的測試資料集（P4）基礎上，自動修復能讓開發人員專注於功能設計而非重複性的除錯工作。

**Independent Test**: 可透過刻意引入一個已知的簡單錯誤（例如修改驗證結果的彙整邏輯），執行自動化測試後觀察系統是否能偵測失敗、產生修復建議、自動套用修復、並重新測試直到通過。

**Acceptance Scenarios**:

1. **Given** 自動化測試執行後偵測到 2 個測試案例失敗, **When** 系統啟動自動修復流程, **Then** 系統分析失敗的測試案例與錯誤訊息，產生程式碼修復建議，自動套用修復後重新執行失敗的測試案例。
2. **Given** 自動修復流程已執行第一輪修復, **When** 重新測試仍有 1 個案例失敗, **Then** 系統繼續分析並嘗試第二輪修復，再次重新測試，直到所有測試通過。
3. **Given** 自動修復流程已達到最大嘗試次數（預設 3 次）, **When** 仍有測試案例未通過, **Then** 系統停止自動修復，輸出完整的修復嘗試紀錄、剩餘失敗的測試案例及錯誤分析報告，交由開發人員手動處理。

---

### User Story 6 - 測試結果報告與歷史追蹤 (Priority: P6)

身為一位開發團隊主管，我希望每次自動化測試的執行結果（包含測試通過率、失敗詳情、自動修復紀錄）都能被記錄並可追蹤，以便了解平行驗證器的品質趨勢與回歸問題。

**Why this priority**: 歷史追蹤提供長期品質可見性，幫助團隊識別頻繁出問題的區域，但其價值建立在前面所有 User Story 的基礎之上。

**Independent Test**: 可透過連續執行多次測試（模擬多次程式碼變更），然後查閱測試歷史報告，確認每次執行的結果、時間戳、修復紀錄都完整記錄且可追溯。

**Acceptance Scenarios**:

1. **Given** 自動化測試已完成執行, **When** 開發人員查閱測試報告, **Then** 報告包含：執行時間、測試總數、通過數、失敗數、每個失敗案例的錯誤詳情、以及自動修復的嘗試紀錄。
2. **Given** 過去一週內已執行 10 次自動化測試, **When** 團隊主管查閱歷史報告, **Then** 可看到每次執行的摘要資訊，並能識別出反覆出現的失敗模式。
3. **Given** 一次測試執行中觸發了自動修復, **When** 查閱該次執行的報告, **Then** 報告包含每輪修復的具體變更內容、修復前後的測試結果差異、以及最終狀態。

---

### Edge Cases

- 當 Bundle 的 entry 為空（0 筆資源）時，系統應直接回傳空的驗證結果，不啟動任何執行緒。
- 當 Bundle 中的某筆 resource 格式嚴重錯誤（例如無法解析為 FHIR 資源）時，該筆驗證失敗不應導致整個平行驗證流程中斷。
- 當伺服器在驗證進行中被要求關閉（graceful shutdown）時，系統應等待正在執行的驗證完成或在合理時間內取消未完成的任務。
- 當多個大型 Bundle 同時提交時，系統的執行緒池應有上限保護，避免執行緒數量無限增長。
- 當 Bundle 中包含巢狀 Bundle（Bundle of Bundles）時，系統應僅平行處理第一層 entry，不遞迴處理巢狀 Bundle。
- 當測試資料集目錄為空或不存在時，系統應輸出清楚的錯誤提示，而非靜默失敗。
- 當基準結果檔案尚未建立時，系統應能執行「首次建立基準」模式，將當前結果儲存為基準。
- 當自動修復過程中修改的程式碼導致編譯失敗時，系統應回滾修改並記錄編譯錯誤。
- 當測試資料集中的 FHIR Bundle 本身格式不合法（例如 JSON 語法錯誤）時，系統應將其標記為「資料集錯誤」而非「驗證失敗」。
- 當平行驗證器的配置參數被修改（例如門檻值、執行緒數）時，測試應能驗證不同配置下的行為是否正確。

## Requirements *(mandatory)*

### Functional Requirements

**核心驗證功能**

- **FR-001**: 系統 MUST 在收到 FHIR Bundle 驗證請求時，自動解析 Bundle 中 entry 陣列的 resource 數量。
- **FR-002**: 系統 MUST 根據 resource 數量與可用系統資源，動態計算最佳並行驗證執行緒數量。
- **FR-003**: 當 resource 數量低於設定門檻時，系統 MUST 採用循序驗證模式。
- **FR-004**: 當 resource 數量達到或超過門檻時，系統 MUST 啟用平行驗證模式，將資源分配至多個執行緒同時驗證。
- **FR-005**: 系統 MUST 在平行驗證過程中監控 CPU 使用率，當使用率接近設定上限時自動調節並行數量。
- **FR-006**: 單一資源的驗證失敗 MUST NOT 導致其他資源的驗證中斷或失敗。
- **FR-007**: 系統 MUST 將所有平行驗證的結果彙整為單一的 OperationOutcome 回應，保留每筆資源的驗證詳情。
- **FR-008**: 平行驗證的結果 MUST 與循序驗證的結果完全一致（結果等價性）。
- **FR-009**: 系統 MUST 提供配置選項，允許管理員調整：平行驗證門檻、最大並行數、CPU 使用率上限。
- **FR-010**: 系統 MUST 使用有界限的執行緒池管理並行驗證任務，防止執行緒數量無限增長。
- **FR-023**: 系統 MUST 預設載入 FHIR R4 基礎規範與 TW Core IG 的 StructureDefinition 作為驗證 Profile。
- **FR-024**: 系統 MUST 支援透過配置載入額外的 IG Profile（如 US Core、IPS），不需修改程式碼。
- **FR-025**: 系統 MUST 對所有 binding 強度（required、extensible、preferred）進行完整的術語驗證，確保 code 值符合對應的 CodeSystem/ValueSet 定義。
- **FR-026**: 當本地未載入某個 CodeSystem 或 ValueSet 定義時，系統 MUST 將該術語驗證視為失敗並回報錯誤，而非靜默跳過。
- **FR-027**: 當資源未在 `meta.profile` 中宣告任何 Profile 時，系統 MUST 自動依據資源類型（如 Patient、Observation）套用對應的已載入 IG Profile（優先 TW Core）進行驗證。

**自動化測試與品質保證**

- **FR-011**: 系統 MUST 提供一組預建的測試資料集，涵蓋以下情境：空 Bundle、小型 Bundle（低於平行門檻）、中型 Bundle（剛好觸發平行）、大型 Bundle（需要完整平行處理）、包含驗證錯誤的 Bundle、混合資源類型的 Bundle。測試資料集 MUST 包含 TW Core IG 官方範例資源（正向案例）以及刻意違規的資源（負向案例），以驗證完整度。
- **FR-012**: 每個測試資料集 MUST 包含對應的預期驗證結果（基準結果），用於自動化比對。
- **FR-013**: 系統 MUST 提供單一指令即可執行所有測試資料集的自動化驗證。
- **FR-014**: 自動化測試 MUST 能比對實際驗證結果與預期基準結果，並明確標示差異項目。
- **FR-015**: 測試資料集 MUST 可擴充，開發人員可依照既定格式新增自訂測試案例。
- **FR-016**: 系統 MUST 支援「首次建立基準」模式，將當前驗證結果儲存為後續測試的比對基準。

**自動修復**

- **FR-017**: 當測試偵測到失敗時，系統 MUST 自動分析失敗原因並產生修復建議。
- **FR-018**: 系統 MUST 能自動套用修復建議到程式碼，並自動重新執行失敗的測試案例。
- **FR-019**: 自動修復流程 MUST 設有最大嘗試次數限制（預設 3 次），避免無限迴圈。
- **FR-020**: 系統 MUST 在自動修復失敗或達到最大嘗試次數時，保留完整的除錯資訊供開發人員手動處理。
- **FR-021**: 自動修復過程中若導致編譯失敗，系統 MUST 自動回滾修改並記錄錯誤。

**測試報告**

- **FR-022**: 每次測試執行的結果 MUST 被記錄，包含：時間戳、測試案例清單、各案例結果、自動修復紀錄。

### Key Entities

- **FHIR Bundle**: 包含多筆 entry 的容器資源，每個 entry 內含一個待驗證的 FHIR resource。是平行驗證的輸入來源。
- **Bundle Entry**: Bundle 中的單一條目，包含一個 resource 和相關的請求資訊。是平行驗證的最小工作單元。
- **驗證結果 (Validation Result)**: 每筆資源驗證後產生的結果，包含通過/失敗狀態及詳細的問題描述。所有結果最終彙整為一個 OperationOutcome。
- **驗證執行緒池 (Validation Thread Pool)**: 管理並行驗證工作者的資源池，具有可配置的大小上限與 CPU 感知的動態調節能力。
- **測試資料集 (Test Dataset)**: 一組預先準備的 FHIR Bundle 檔案，每個檔案代表一個特定的測試情境，搭配對應的預期驗證結果。
- **基準結果 (Baseline Result)**: 每個測試資料集的預期驗證輸出，作為後續測試比對的標準答案。首次可由系統自動產生。
- **修復紀錄 (Fix Record)**: 自動修復流程中每一輪嘗試的詳細記錄，包含修改的檔案、變更內容、修復後的測試結果。

## Success Criteria *(mandatory)*

### Measurable Outcomes

**驗證效能**

- **SC-001**: 包含 50 筆以上 entry 的 Bundle 驗證時間，相較於循序驗證至少縮短 40%。
- **SC-002**: 平行驗證執行期間，系統 CPU 使用率不超過管理員設定的上限（預設 80%）。
- **SC-003**: 無論使用平行或循序模式，相同 Bundle 的驗證結果完全一致，正確率 100%。
- **SC-012**: TW Core IG 官方範例資源 MUST 100% 通過驗證（正向完整度），刻意違規的資源 MUST 100% 被正確拒絕（負向完整度）。
- **SC-004**: 系統在平行驗證大型 Bundle 的同時，仍能正常回應其他使用者的請求，回應時間增幅不超過 20%。
- **SC-005**: 管理員可在不修改程式碼的情況下，透過配置調整平行驗證的所有行為參數。

**測試與品質保證**

- **SC-006**: 測試資料集至少涵蓋 6 種不同情境的 FHIR Bundle，確保覆蓋空集合、小型、中型、大型、含錯誤、混合類型等場景。
- **SC-007**: 開發人員在修改程式碼後，可透過單一指令在 5 分鐘內完成所有測試案例的執行與結果比對。
- **SC-008**: 對於可自動修復的簡單問題（例如格式錯誤、參數遺漏），自動修復成功率達到 80% 以上。
- **SC-009**: 自動修復迴圈在最大嘗試次數內完成，不會造成無限迴圈或系統資源耗盡。
- **SC-010**: 測試報告格式清晰，開發人員可在 1 分鐘內從報告中定位失敗的測試案例及其原因。
- **SC-011**: 新增一個自訂測試案例（含資料集和基準結果）不超過 10 分鐘。

## Clarifications

### Session 2026-02-08

- Q: 驗證時應套用哪些 Profile？ → A: 預設 FHIR R4 基礎規範 + TW Core IG，但架構上保持彈性，支援透過配置載入額外 IG Profile（如 US Core、IPS 等）。
- Q: 驗證深度是否包含術語綁定？ → A: 完整驗證所有 binding 強度（required + extensible + preferred），確保最嚴格的合規性。
- Q: 本地查不到 CodeSystem/ValueSet 時如何處理？ → A: 強制完整驗證，本地查不到時視為驗證失敗，確保不會漏掉任何術語約束。
- Q: 資源未宣告 meta.profile 時如何驗證？ → A: 自動按資源類型套用對應的 TW Core Profile 進行驗證，確保即使未宣告也能合規。
- Q: 如何量化驗證完整度？ → A: 使用 TW Core IG 官方發布的範例資源作為正向基準，加上自訂的負向測試案例（刻意違規的資源），以確保驗證器能正確通過合規資源並拒絕不合規資源。
- Q: 門檻切換邏輯應在哪個專案實作？ → A: 選擇方案 A — 修改 hapi-fhir core（fork: Phiosn-Daniel/hapi-fhir, branch: daniel_core）的 FhirValidator.doValidate()，在 core 層面加入門檻判斷邏輯，確保 thread-safe 且架構乾淨。Starter 專案負責配置傳遞。

## Assumptions

- 系統執行環境至少具備 2 核以上的 CPU，平行驗證才有實質效益。單核環境下將自動降級為循序驗證。
- FHIR Bundle 中的各筆 entry resource 可獨立驗證，彼此之間不存在驗證順序依賴關係。
- CPU 使用率的偵測以作業系統層級的指標為依據，採樣間隔需在合理範圍內（例如每秒一次），避免過度消耗監控資源。
- 預設配置值為：平行驗證門檻 = 10 筆、最大並行執行緒數 = CPU 核心數、CPU 使用率上限 = 80%。
- 巢狀 Bundle（Bundle of Bundles）僅平行處理第一層 entry，不遞迴展開處理。
- 自動修復功能依賴 AI 輔助（如 Cursor IDE 的 Agent 模式）來分析失敗原因與產生修復建議。系統本身提供錯誤分析報告，由 AI 工具解讀並執行修復。
- 測試資料集使用 JSON 格式的 FHIR Bundle，存放在專案的固定目錄中（例如 `src/test/resources/bundles/`）。
- 基準結果以結構化格式儲存（例如 JSON），支援自動化比對且可被版本控制追蹤。
- 自動修復適用於邏輯簡單、範圍明確的問題。複雜的架構性問題仍需人工介入。
